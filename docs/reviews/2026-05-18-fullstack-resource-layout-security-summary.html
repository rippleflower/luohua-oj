Full-Stack Review

全栈资源、布局与安全总览

本审查摘要基于当前仓库的静态实现，对 web、admin-web、API/auth 的资源组织、页面布局、接口暴露面与 Web 安全边界做结构化总结。重点不是渗透测试，而是明确当前边界是否清晰，以及未来最容易把系统从“边界明确”拖向“风险模糊”的扩展点。

前端执行面 未发现 dangerouslySetInnerHTML、innerHTML、eval 或显式脚本注入入口。
认证与写操作 当前采用 HttpOnly session cookie + 可读 CSRF cookie + X-CSRF-Token 回传。
权限边界 后台菜单只负责可见性，真正授权仍在服务端 requireAdminPermission。

接口暴露面与边界

公共读接口

  • /problems、/problems/{slug}
  • /contests、/contests/{slug}
  • /submissions/*、/users/{username}/submissions

认证与个人中心

  • /auth/* 负责注册、登录、会话与密码变更
  • /me/* 负责个人摘要、设置、资料更新
  • 读写边界按 cookie 会话与 CSRF 中间件分开控制

后台接口

  • /admin/* 由认证中间件统一包裹
  • 写接口叠加 requireCSRF
  • 能力按 view / edit / publish / system / audit 分层
Security

静态安全审查

已有防线

  • 未见危险 HTML 注入或动态代码执行入口。
  • session cookie 为 HttpOnly + SameSite=Lax，前端不直接持有主会话凭证。
  • 写请求通过 oj_csrf cookie 与 X-CSRF-Token 进行双提交校验。
  • 后台关键写路由同时受服务端权限中间件保护。

当前未见高危，但要持续看守

  • 前台错误回显较克制，但后台 UI 会显示后端 error 文案，后端必须继续把错误收口成业务级消息。
  • localStorage 当前不承载 session token，这是好边界，后续不要把敏感状态迁入。
  • infra/env/*.example 仅为样例配置，不含实密钥，但对系统依赖暴露是明确的。

后续最易引入漏洞的位置

  • 若题面、公告或运营内容改为 HTML 富文本渲染，XSS 风险会显著上升。
  • 若对象存储链接、外链跳转、附件下载缺少白名单或内容类型控制，暴露面会扩大。
  • 若为调试方便把数据库/对象存储/内部路径错误直接回显到前端，信息泄露风险会上升。

品牌映射建议

当前站点并未使用本次品牌指导色板。若需要把审查产物包装成统一风格，建议只对报告本身应用以下映射，而不要误写成“现站已完成品牌对齐”：

  • 浅底：#faf9f5
  • 中灰：#b0aea5
  • 强调色：#d97757 / #6a9bcc / #788c5d
  • 标题字体：Poppins, Arial, sans-serif
  • 正文字体：Lora, Georgia, serif

Conclusion

当前实现最有价值的特点不是“已经做完所有安全工作”，而是基础边界清晰：结构化渲染、cookie 职责分离、写操作 CSRF、防菜单即授权误区。后续如果继续保持这条边界，并把富文本、外链、对象存储与原始错误透传控制住，系统短期内不会因为前端资源和布局扩展而自然滑向高危状态。
